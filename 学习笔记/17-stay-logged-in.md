# 学习笔记 17:保持登录(关掉 App 再打开还是同一个账号)

## 原来的状态
其实 App 一开始就把令牌存在了 Keychain 里,重开 App 会自动恢复登录。但有三个漏洞,所以「感觉上」经常掉登录:

| 漏洞 | 后果 |
|---|---|
| 会话固定 7 天过期,不管你有没有在用 | 每周必须重新登录一次 |
| 启动时服务器连不上 → 界面显示成未登录,之后也不再确认 | 网络不好时打开 App,看起来像被登出了 |
| 令牌不分服务器,只存一份 | 切换服务器地址(或者我跑自动测试时)会把原来的登录冲掉。**你之前要注册 ren2 就是这个原因** |

## 怎么改的
### 服务器:滑动过期(`app/routers/auth.py` 的 `/me`)
- 网页和 App 每次启动都会调 `/api/auth/me`。在这里顺便把过期时间往后推。
- 效果:**一直在用就一直不过期;连续 7 天完全不用才过期**。这叫滑动过期(sliding expiration)。
- 不是每次都写数据库:只有剩余时间不到一半时才延长(否则每次启动都多一次写入)。
- 「要不要延长」的判断写在 SQL 的 WHERE 里(`expires_at < now + ttl/2`),不是先读出来在 Python 里比较——又是「先读后写」会出问题的地方,而且 SQLite 取回的时间不带时区,在 Python 里比容易错。
- 网页用的 Cookie 自己也有期限,所以延长时把 Cookie 重新发一次;App(Bearer)不发 Cookie。

### iOS
- **令牌按服务器分别保存**(`Keychain.swift`):Keychain 的条目名从 `accessToken` 改成 `accessToken@服务器地址`。旧版存的那一份,第一次读取时自动搬到当前服务器名下。
- **记住用户名**(`AppState.swift`):用户名不是秘密,存在 UserDefaults。启动时先用它把界面显示成已登录,不用等服务器回答。
- **确认推迟到连得上的时候**:启动时连不上不算登出;等 WebSocket 连上、或 App 回到前台时再向服务器确认。只有服务器明确回答 401,才清掉登录。

## 为什么令牌放 Keychain、用户名放 UserDefaults
- 令牌 = 能代表你操作的钥匙 → 必须加密保存(Keychain)。
- 用户名 = 画面上本来就显示的东西 → 普通保存就行(UserDefaults)。
- 原则:**按「泄露了会怎样」决定放哪里**,不是一律用最严的。

## 安全上的代价(面试可能会问)
- 滑动过期意味着:令牌如果被偷,只要对方一直用,就一直有效。对策是已有的那些:令牌只存哈希、可以登出、每台设备独立。更严格的做法是「滑动过期 + 绝对上限(比如最长 90 天)」,这次没做。

## 测试
- pytest:剩余不到一半 → 延长并重发 Cookie;刚登录的 → 不改;Bearer → 延长但不发 Cookie。
- UI 测试:关掉再打开还是同一账号、购物车还在;换服务器地址 → 是未登录,换回来 → 原账号还在;登出后重开 → 未登录;服务器停着时启动 → 仍显示已登录,服务器恢复后不用重新登录就能发弹幕。

## 追记:测试变得不稳定的原因
加了「重开 App」的测试之后,全部测试一起跑时,主流程会卡在「注册时输入密码」不动(单独跑却能过)。
- 原因:iOS 的密码自动填充。前面的测试登录过之后,系统开始在密码框上弹出建议、询问「保存密码?」,这些是**系统的画面**,会抢走测试的点击和输入。
- 对策:测试启动 App 时带上 `--ui-testing` 参数,App 看到它就不给输入框标注「这是用户名/密码」,系统就不介入了(`Config.swift` 的 `isUITesting`、`AccountViews.swift`)。正式使用时照常标注,自动填充功能不受影响。
- 教训:**单独跑能过、一起跑失败**,多半是测试之间通过某个共享的状态互相影响(这次是系统记住的密码)。
